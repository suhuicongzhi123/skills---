# 后期维护规范

## 1. 核心原则：只做减法与原位修正，不做增量补丁

库的体量只能随「新增覆盖领域」增长，不能随「纠错次数」增长。

| 场景 | 允许做法 | 禁止做法 |
|---|---|---|
| 事实错误 | 直接改写原句为正确表述 | 加「（更正：……）」「旧版说法有误」等注释 |
| 规则失效 | 删除旧规则，原位写新规则 | 新规则追加在旧规则后面并存 |
| 内容重复 | 保留权威出处一处，其余删除并改路径指引 | 两处都留、互相标「参见」 |
| 文件过时 | 整体删除文件并清理路由树与索引中的条目 | 标注「已废弃」继续占位 |
| 措辞优化 | 直接替换 | 保留原句再附优化版 |

## 2. 禁止的维护形态

1. 注释式纠错：任何 `【修正】【旧版】【注意此处以前写错】` 类痕迹。
2. 打补丁式追加：在文件末尾不断追加补充说明，导致同一问题散落多处。
3. 个人备注：维护者的思考过程、未定论的草稿不进入库文件；待核实内容用「待核实」标签明确标注并写清缺口。
4. 无版本登记的修改：每次改动必须同步更新文件头版本注释，并在 `版本策略.md` 历史表登记一行。

## 3. 体量控制

- 单文件软上限约 300 行；触顶后按子主题拆分，不依靠压缩字号或删注释硬撑。
- 每次维护结束检查路由树：所有被删文件、改名文件的引用必须同步更新，不得留死链。
- 新增文件前先检索是否已有同主题文件；能扩写既有文件的，不新建。

## 4. 规则数据维护

- 机械检查的词条与正则集中在 `scripts/rules/` 下的 JSON 文件，维护时只改 JSON。
- 每条规则带稳定 ID（如 `ACT-HD-01`），ID 不复用：规则删除后 ID 作废，新规则用新 ID，保证历史审查报告可追溯。
- 配置 JSON 的字段 schema（amputations/code 键名、devices 扁平列表、type 与 side 取值等）以 `scripts/mechanical_check.py` 文件头说明为唯一权威口径；`anatomy.json` 增删平面代码时，同步更新该说明中的 code 清单。
- JSON 修改后必须运行一次 `scripts/mechanical_check.py` 自测，确认脚本可正常加载规则。

## 5. 事实类内容的维护依据

- 医学事实以权威来源（医学机构页面、教材、ISO 术语标准等）为准，修改时在文件内「来源」小节记录来源名称与查阅日期，不贴长段原文。
- 来源之间冲突时，优先术语标准与临床教材；无法判定的，写「待核实」并列出冲突点，不选边下定论。
