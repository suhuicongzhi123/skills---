# 开发者恢复规范

适用场景：新会话开始、上下文被清空、更换写作者代理后，需要无偏差接手一个进行中的写作项目。

## 1. 恢复顺序（不得跳步）

1. 读 `SKILL.md`，确认本库的工作铁律与路由树。
2. 读本文件，明确恢复清单。
3. 读 `references/00_治理/版本策略.md`，确认技能库当前版本；若项目记录了适配库版本，检查是否存在主版本差异。
4. 定位项目目录（默认在用户指定的作品文件夹内；未指定时询问用户，禁止猜测路径）。
5. 依次读取项目状态文件，顺序如下：
   - 作品设定总表（题材、世界观、设定豁免与风格豁免登记）
   - 全部角色卡
   - 辅具连续账（最新章节末状态）
   - 伏笔与一致性台账
   - 最近一章定稿与最近一份审查报告
6. 向用户口头复述：题材方向、主要角色及其截肢配置、当前进度（已定稿到第几章）、待办事项，请用户确认后再动笔。

## 2. 项目目录标准结构

每个小说项目独立一个目录，建议结构：

```text
<作品名>/
├── 作品设定总表.md          # 从 assets 模板复制
├── 角色/
│   └── <角色名>_角色卡.md    # 每个角色一个文件
├── 辅具连续账.md            # 全局唯一，跨章节累积
├── 伏笔与一致性台账.md
├── 章节/
│   ├── 第01章_草稿.md
│   ├── 第01章_审查报告.md
│   └── 第01章_定稿.md
└── 自查输出/                # 机械脚本生成的报告
```

## 3. 禁止事项

- 禁止凭印象补全缺失的项目状态。文件缺失或记录矛盾时，列入恢复报告请用户裁决。
- 禁止在未读取角色卡的情况下撰写有该角色出场的章节。
- 禁止跳过机械自查与冷读稽查直接定稿。
- 禁止恢复后自动续写。恢复完成后只汇报状态，等待用户指令。

## 4. 版本不一致处理

- 库主版本（X.0.0）升级后，旧项目继续按旧版本约定写完，或经用户明确同意后迁移；迁移需逐文件核对，不得静默替换。
- 次版本与补丁版本升级默认兼容，直接使用新版库文件。

## 5. 会话内压缩恢复协议

第 1 至 4 节管新会话接手；本节管同一会话内上下文被压缩后的自救。压缩丢掉的不是状态（草稿、台账、报告都已落盘），是注入：事实禁令、章纲、人物细节最容易被摘要吞掉。

触发自检：每次接到写作或续写指令时，先问自己能否复述本章相关的事实禁令与章纲落点；不能即判定疑似被压缩，按下列最小集顺序重读，不重建全量上下文：

1. 本章出场角色对应的生理事实小类文件与 `../02_生理事实/禁忌动作总表.md`（含未登记动作判定流程）。
2. 本章草稿与章纲任务书（承接点五维、落点）。
3. 作品设定总表的题材、豁免登记与文风契约。
4. 辅具连续账最新状态、伏笔与一致性台账（含文风指纹账近 5 章）。
5. 上一章定稿末尾约 500 字，衔接风格与钩子。

第 3、4 件不可只回读坐标：只恢复禁令不恢复人物，会写出合规但呆板的动作执行体；只恢复人物不恢复文风坐标，会单章合规、全书换腔。恢复后在审查报告或工作记录中留一行恢复留痕；连续两章触发压缩恢复，提示用户考虑缩短单次任务跨度。
