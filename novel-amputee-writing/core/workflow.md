## 〇、工作流模式（flash / pro / max）

> 模式在人物设定阶段收集流程**第 13 题（末题）选定**，开书后全书锁定（中途切换须告知用户
> 账本衔接方案）。三模式共享：大纲质量闸、章八要素、严重错误六类合一闸、章末核查清单
> ——模式只改变「写作与审查的分工方式」，不豁免任何质量闸。

| 模式 | 定位 | 分工 | 适用 |
|---|---|---|---|
| **flash** | 自写自审 | 单代理：写作＋章末自查（含六类合一闸） | 快速成稿/短篇/试笔 |
| **pro** | 一写一审 | 主代理写作＋自查 → **独立冷读子代理**逐章稽查 → 主代理修正＋记账 | 中长篇默认推荐 |
| **max** | 队长＋队员 | **队长**（主代理）：剧情安排与整体把控，不写正文；**写作员**：成文；**审查员**：冷读稽查；**记账员**：账本更新 | 长篇/多线复杂/最高质量要求 |

**章级审查深度分级**

> 模式选定即全书锁定、**产物集与角色不可降级**（这条不变）。但"稽查要做几轮"属于**深度**，
> 不属于模式——把它按章级风险分级，不动模式与产物集。

| 档 | 内容 | 适用 | 禁区 |
|---|---|---|---|
| **全审**（默认） | 常规稽查 + 一轮复核（复核可针对改动项） | 所有章 | — |
| **简审** | 常规稽查一轮，不做复核轮 | 张力级 ≤2 的呼吸章、无对抗的日常章 | ❌ 首 3 章 · ❌ 弧线 crisis 章 · ❌ 卷末章 · ❌ 含 B/C 档亲密戏的章 · ❌ 含战斗/追逐/围堵的章 |

- 简审**不改产物集**：七问＋13 维报告、引文实证、指纹、机检全部照旧（gatecheck 不受影响），只是少一轮复核
- 简审须在账本 `工作流执行日志.审查深度` 注明「简审」及理由；未注明的按全审判
- **复核轮的定义**：主代理/队长据报告修正后，**审查员**（独立上下文）对修正稿做第二轮核验——
  只核上轮「不通过」项与改动段落，不重跑 13 维；结论追加在同一份审查报告 `## 复核` 段
  （改动项｜是否解决｜新问题），**不新增产物**。复核不得由写作主体自核
  （口径见 `core/cold-review.md#八、调用方式`）
- **简审升全审**：简审章修正改动 >3 处，或触及章末钩子 / 核心受限 / 生理事实 → 自动升为全审，
  补做复核轮后再过交付闸（防「简审＋大改」绕过复核）

**各模式章循环**：

> **交付前最后一步（三模式统一）——自问：脚本跑了吗？**
> 有 gatecheck 的 PASS 输出 → 才可交付；没有 → **立即运行**，不得交付。
> 这一问是硬性显性步骤，不是提醒——跳过它直接交付＝严重制度失败（SKILL 三 第 6 类）。

- **flash**：写当前章 → 章末自查（四条铁则执行）→ 更新账本 → **运行 gatecheck（自问：脚本跑了吗？）→ PASS** → 携机检披露交付 → 等用户确认 → 下一章
- **pro**：写当前章 → 章末自查 → 冷读稽查（`core/cold-review.md` 七问＋13 维）→ 据报告修正 → **复核轮（全审；审查员核不通过项与改动段）** → 更新账本 → **运行 gatecheck（自问：脚本跑了吗？）→ PASS** → 携机检披露交付 → 等用户确认 → 下一章
- **max**（队长视角）：排章派单 → 收草稿 → 快检 → 审查员稽查 → 裁定修正（小错自改，大错回炉写作员）→ **复核轮（全审；审查员核改动项）** → 定稿 → 记账员落账 → 队长终审 → **运行 gatecheck（自问：脚本跑了吗？）→ PASS** → 携机检披露交付 → 等用户确认 → 下一章

**max 模式职责细则**（各角色上岗声明＝该角色的行为契约，随任务包传递）：

- **队长（主代理）**：大纲与弧线把控、每章任务包编制（章八要素＋场景要求＋受限配额＋
  注入文件清单）、基调与主冲突线配额监控、审查报告裁定、账本终审——**不亲自写正文**。
  上岗自认：我是工坊主理人，对整本书负责——订单（大纲契约）在我手里，
  走货路线（基调循环）不换道，交出去的每章都有完整手续
- **写作员（子代理）**：领任务包成文；交草稿前完成章末自查（四条铁则留痕随草稿一并提交）；
  不自改账本、不自行扩章。上岗自认：我是领活的写手——生理事实零错是本分，
  受限戏是主菜，任务包之外的需求交回队长，不自作主张
- **审查员（子代理）**：按 `core/cold-review.md` 全维度稽查草稿（独立上下文），
  只出报告不改文
- **记账员（子代理）**：按**定稿章**更新账本（本章登记/情节事件登记/distribution/
  核查记录）——max 模式下**唯一写账者**，防双账本。上岗自认：我是唯一写账的
  账房，原则是账实相符——没发生的流程不登记，登记的数字必须与产物对得上
- 交接一律**文件化中转**（章任务包 / 章草稿 / 审查报告均落盘于小说项目工作区），
  禁止超长上下文内联传递
- **章任务包的承载**：用 `templates/chapter.md` 章节信息区（队长填齐章八要素＋受限
   设计＋注入文件清单后落盘为**章任务包文件**交付写作员）——不另设任务包模板；
   **写作员另建章草稿文件续写正文**（❌ 不在任务包文件上续写——任务包→队长指纹、草稿→写作员指纹，
   两产物须独立落盘、末行指纹互异，见卡口③与 gatecheck 产物三验）
- **选定模式全书锁定，禁止偷工降级**：子代理调用临时失败 → 重新调用直至成功，
  不得改跑更低模式交付——违规章按选定模式重跑完整流程。
  （⚠ 与容量降级区分：小上下文机型因压缩频发需 pro→flash 属**容量降级**，须按 `PLATFORM-CN.md`
  显式声明并登记账本 `工作流执行日志`，非偷工；两者语义不同。）

**单上下文分角色扮演 ≠ 子代理调用**：同一上下文里切换「现在我是审查员」继续
干活，没有全新上下文与宿主任务实例，**本质是自审伪装成多人**——判假执行
（`SKILL.md#三` 假执行判定第 3 形态）

## 一、执行完整性硬卡口

> **口头声明 ≠ 执行**：宣称某模式≠实际执行该模式。执行以**证据链**为准
> （账本 `工作流执行日志` ＋ 产物文件）；无证据＝未执行。三卡口＋交付闸如下，
> 每章交付用户前必过（三种模式同适用，卡口②③按模式有「不适用」态）。

**卡口① 自查全覆盖**：章末自查报告须**逐一列出** `templates/chapter.md` 核查清单
**全部条目**（剧情结构/受限与不便/严重错误六类合一闸/一致性/成文质量关/文学自评），
每项留痕三件套（**S ID｜判定｜项名｜证据**；判定必须在第二列——机检按 `Sxx｜判定` 折算维度），
报告末尾报**「X/X 全查」总计数**——
缺任一项＝该项未查，卡口不通过（铁则⑤）。

**卡口② 稽查全覆盖**（pro/max 适用，flash＝不适用）：冷读报告须含
`core/cold-review.md` **全部 22 个维度的逐项判定**（维度号｜判定｜结论）。
受理前先验覆盖数：**七问 7 行＋必判 13 维齐全才可受理**；缺项 → 退回子代理补查，
**不得据不全报告修正与交付**。
> **受理六判据的判定主体**：①覆盖数/②生成指纹/③输入隔离/⑤引文/⑥主语由 `core/cold-review.md#八、调用方式`
> 受理前验收；其中**④「独立发现」是否「自查未发现」由主代理受理时比对裁定**（审查员依③看不到自查报告，
> 机检 `gatecheck.py` [13] 同源判定提供信号），不要求审查员自证——详见本文档下方
> `#冷读报告受理验收流程` 与 `core/cold-review.md#八、调用方式`。

### 1.1 冷读报告受理验收流程（pro/max 模式）

> **触发时机**：审查员提交冷读报告后，主代理（pro模式）或队长（max模式）受理前必做。

**验收步骤**（按顺序执行）：

1. **覆盖数验证**（卡口②）
   - [ ] 七问 7 行齐全
   - [ ] 必判 13 维齐全（维度号｜判定｜结论）
   - 缺项 → 退回补查，不继续后续步骤

2. **生成指纹验证**（gatecheck [6]）
   - [ ] 审查报告末行有 `生成指纹: X`
   - [ ] 指纹 = 审查员凭证（与自查报告、草稿指纹互异）
   - 无指纹或指纹重复 → FAIL

3. **输入隔离验证**（gatecheck [8]）
   - [ ] 审查员的提示词**未含**自查报告
   - [ ] 审查员的输入只有：草稿+规则包（不含写作卡+自查）
   - 隔离失败 → 退回重审（新上下文）

4. **引文实证验证**（gatecheck [11]）
   - [ ] 报告中的引文确实来自草稿原文
   - [ ] 引文位置标注正确（章号/段号/句首）
   - 伪造引文 → FAIL

5. **主语纯净验证**（gatecheck [12]）
   - [ ] 审查报告主语无 "我写""作为队长""上文提到"
   - [ ] 无自证话术（"没看到自查报告""我独立发现"）
   - 主语不纯 → 退回改写

6. **独立发现判定**（人工复核 + 机检辅助）
   
   **机检信号**（gatecheck [13]）：
   - 审查22维判定向量 vs 自查S编号折算向量
   - 一致比例 ≥95% → WARN（同源信号）
   - 一致比例 <95% → 未触发
   
   **人工复核**（主代理/队长执行）：
   
   a. **如果机检未触发（<95%）**：
      - [ ] 审查侧有 ≥1 条不通过 / 反证轮 ≥3 段实质核验
      - 满足 → 视为独立发现，通过
      - 不满足 → 审查流于形式，退回重审
   
   b. **如果机检触发 WARN（≥95%）**：
      - [ ] 对比引文：审查引用的句子 vs 自查引用的句子
        - 引文完全相同 + 位置相同 → **疑似复制粘贴**
        - 引文不同 或 位置不同 → 合法同判（继续下一步）
      
      - [ ] 检查判定依据：审查报告的论证 vs 自查报告的论证
        - 论证路径相似度过高 → **疑似抄袭**
        - 论证路径不同（从不同角度得出相同结论）→ 合法同判
      
      - [ ] 人工读一遍：不通过项确实有问题吗？
        - 确实有问题 → 合法同判，通过
        - 问题不成立 → 审查员误判或造假，退回重审
   
   **裁定**：
   - ✅ **合法同判**（引文/位置/论证路径不同，但结论一致）→ 接受报告
   - ❌ **伪装同源**（复制粘贴或抄袭判定）→ 退回重审（新上下文、新审查员）
   - ⚠️ **边界情况**（一致率90-94%）→ 人工读报告，判断质量是否达标

**记录留痕**（max模式必须，pro模式建议）：
- 在账本 `工作流执行日志` 记录本章验收结果
- 格式：`章X 冷读验收：[通过/退回] | 同源信号：[是/否] | 裁定：[合法同判/独立发现]`

**常见问题处理**：
- **Q**: 同源信号触发，但审查确实发现了新问题怎么办？
- **A**: 只要引文/论证路径不同，即为合法同判，接受报告。一致率高不等于造假。

- **Q**: 审查员说"我独立发现"算不算自证？
- **A**: 算。主语纯净要求审查员不自证，由主代理/队长裁定独立性。

- **Q**: 一致率刚好95%怎么判？
- **A**: 触发WARN，进入人工复核流程。

**卡口③ 模式执行保真**：实际调用与产物须匹配选定模式的必需集——

| 模式 | 必需代理 | 必需产物（落盘文件） |
|---|---|---|
| flash | 本体 | 章草稿＋自查报告 |
| pro | 本体＋冷读子代理 | 章草稿＋自查报告＋审查报告 |
| max | 队长＋写作员＋审查员＋记账员（**各自独立**，不得合并扮演） | 大纲（首章前置）＋章任务包＋章草稿＋审查报告＋自查报告＋记账摘要（记账员） |

- **调用凭证化**：pro/max 模式下 `调用代理` 逐角色登记**宿主调用凭证**
  （任务/会话标识，如 `ses_xxx`/`task_id`）；无凭证的「名字列表」＝未经验证的
  声明＝机检 FAIL
  - **两段式登记**：宿主返回的实例 ID 只在子代理**交付之后**
    才拿得到，而产物末行的指纹必须在**交付之前**写进去——两者在时间上不可同时满足，
    所以凭证只能两段走：
    ① 子代理在产物末行写**自定标识**（如 `agt-wr-04`，同章各角色互异）；
    ② 调用返回后，由**记账员**把宿主真实 ID 回填账本 `调用代理.宿主编号`；
    机检比对的是①（唯一可比对的字段），②是留给冷读与人工追溯的证据。
    说明：①本质是自签，**能防"多角色合一扮演"，防不了"整章伪造"**；
    防伪仍靠产物内容（引文实证、独立发现、反证轮）。
- **子代理产物指纹**：每个产物文件末行带 `生成指纹: <该产物签发角色的凭证>`——
  指纹与账本对应角色凭证同号（角色↔产物映射：max 章任务包→队长、章草稿/自查
  报告→写作员、审查报告→审查员、**记账摘要→记账员**；pro 章草稿/自查报告→本体、审查报告→冷读）；
  **同一章内各角色凭证两两互异**（同凭证签发多角色产物＝合并扮演实锤）；
  指纹不同号/缺指纹行＝机检 FAIL
- **假执行判定**（三种形态，命中任一 → 该章**不得交付**，按选定模式重跑完整
  流程，不得降级交付）：
  1. 宣称 max 实跑 pro/flash（无写作员/记账员调用记录或无对应产物）
  2. 宣称 pro 实跑自审（无冷读报告）
  3. **单上下文分角色扮演冒充多人**（无宿主任务实例的自称「审查员/写作员」）
     ——写作/自查/冷读同主体完成却登记多人；同凭证签发多角色产物同判
- 逐章登记进账本 `工作流执行日志`（选定模式/实际执行模式/审查深度/调用代理＋凭证/产物/
  三卡口判定）

**PASS 印章**：gatecheck 每次 PASS 自动为各章生成
`gate-pass-第N章.txt`（**交付凭证**：正文SHA＝sha256(章草稿)[:16]＋正文字数
＋印章＝sha256(章号+章草稿+自查报告+审查报告)[:16]，**脚本生成，手写无效**；
FAIL 运行不生成凭证）；任何产物事后篡改或手写伪造 → 下次机检重算比对 FAIL →
该章须重跑完整流程重新过闸。「下章开写前必重验上章凭证」为固定环节
（每章循环首步），伪造历史在任何后续真跑中被揭穿。

**交付正文绑定（正文与脚本深度绑定）**：向用户交付的正文**必须逐字节来自
被机检的章草稿文件**——章草稿为三模式必需产物，无草稿＝无交付物＝机检 FAIL；
交付正文时**随正文附 gate-pass 凭证内的「正文SHA」与「正文字数」**（贴出即可，
不要求用户做任何判断——但正文若与被检文件不一致，SHA 立即可见地不符）；
交付后被换正文 → 下章开写前重验时 SHA/印章不符 → FAIL → 该章重跑完整流程。

**定稿改名（交付闸 PASS 之后立刻做）**：

交付闸 PASS 之后，章稿已经过「自查→冷读→修正→复核→机检」五道，
它**不再是草稿**。须当场完成四件事，缺一件即视为流程未闭环：

1. 把 `第N章-草稿.md` 重命名为 `第N章-定稿.md`
2. 账本 `工作流执行日志.产物.章草稿` 同步改为新文件名（不改名会找不到文件，下次机检直接 FAIL）
3. **把 `本章登记` 的摘要键 append 到 `章节登记归档`**（见下「登记归档」）
4. 再跑一次 gatecheck 确认 PASS（改名不改内容，正文 SHA 不变，印章继续有效）

> **为什么要有这一步**：实测中曾出现「一章已经改到第五稿、冷读复核全过、闸也过了，
> 文件却还叫『草稿』」。后果有三：① 事后分不清哪一份是交付版，哪一份是过程稿；
> ② 目录里堆满 `-草稿`，作者自己也要打开才知道哪版能用；③ 交付给用户的文件名
> 自认「未完成」，读者一看就减分。
>
> **命名约定**：`-草稿` ＝ 还在改；`-定稿` ＝ 已过闸、即交付版。
> 中途多稿可以在草稿阶段用 `-草稿2`、`-草稿3`，但**过闸那一刻必须归一到 `-定稿`**。

**账本体检（写之前先跑）**：

填账本之前先跑一次体检，把「填完才发现结构错」提前拦掉：

```bash
python scripts/ledger_lint.py <项目目录>/state-ledger.yaml
```

查四件事：① YAML 能否解析（错在哪一行、哪一类）；② 顶层键重复（后者静默覆盖前者）；
③ **父键被当标量填了值**（最高频的一类错，会让子键悬空）；④ 逐章必填是否为空。

> **为什么要有这一步**：实测两章，账本填充各失败 4 次，全是同一类——把父键当标量填。
> 模板里已经写了「哪些是父键」，但**填的时候不会去读那段注释**。
> 人写、机器查，比「靠人记得住」可靠。填完再跑一次，两次都 PASS 才算账本可用。

**登记归档**：

`本章登记` 是**单章结构**——写完下一章就被覆盖。历史章的 beat／turn／章末钩型／
受限 beat 全部消失，于是：

- 任何「与近 5 章比对」的检查（钩型不重复、受限层级配比、章节功能配比）**都缺数据源**；
- 事后复盘「第 3 章的 turn 是什么」查不到；
- 曾导致一条检查误报：拿当前章的字段去校验历史章（见 `gatecheck` [20] 的当前章限定）。

所以每章交付时，把 `本章登记` 的**摘要键**追加一条到 `章节登记归档`（键名相同，
不必整块照抄）。只记这几项即可：`章 / 张力级 / 节拍角色 / 章节功能 / 主冲突线beat /
受限beat（层级＋类型）/ 章末钩子类型 / 钩子兑现锚 / 大纲对齐`。

用 gatecheck 的 `[24]` 自查是否漏记：归档里缺章号 → WARN。

**交付闸（合并判定）**：卡口①②③全过（含「不适用」态）→ 方可向用户交付本章；
任一未过 → **不得交付**，补执行缺项后重过闸。「等用户确认进入下一章」的例外①
以交付闸通过为前提——未过闸的章不存在「等确认」，只存在「补执行」。

**脚本运行显性条件＋披露义务（针对脚本漏跑——严重制度失败的处置）**：

- **脚本运行＝交付的显性前置条件**：gatecheck 实际运行并输出 PASS 是
  「交付闸: 通过」的唯一合法来源——账本登记「通过」但无脚本运行记录＝
  该登记无效，交付无效
- **对话中披露（每章交付必附）**：向用户交付正文时，交付信息末尾**必须**
  附机检披露行——`机检：PASS（第N章，gatecheck 全项通过）`；无此行的交付
  ＝脚本漏跑嫌疑交付，用户可直接拒收
- **漏跑即严重制度失败**：跳过 gatecheck 直接交付（或事后发现未跑）＝
  **严重制度失败**（`SKILL.md#三` 第 6 类）——须在对话中**如实披露**
  「脚本漏跑——本交付无效」，立即补跑脚本，FAIL 则修复后重跑，重新交付；
  隐瞒漏跑不报＝制度失败＋诚信违规双重叠加
- **自问机制（防惯性遗忘）**：每章交付动作发出前的最后一问固定为
  **「脚本跑了吗？」**——自问无 PASS 证据 → 停止交付、先跑脚本；
  该自问写进章循环与章末核查清单，是显性步骤不是心理暗示
- **执行日志登记**：`工作流执行日志` 增 `机检运行` 字段（是｜否＋输出结论）——
  「是」须对应本次会话实际执行的脚本运行；填「是」但拿不出 PASS 输出＝
  又一层假登记；机检校验该字段须为「是」

**机检条款（能跑 python 的环境强制）**：交付闸以脚本输出为准——
`python scripts/gatecheck.py <小说项目目录>`（可加 `--chapter N` 指定关注章——
**不豁免其余章检查**，历史章 FAIL 一并报整体 FAIL，防展示性通过），
**输出 PASS 才算过闸**。机检项＝结构与覆盖（日志完整性/章号连续/模式保真
——选定≠实际一律 FAIL，不得降级/代理凭证化＋凭证互异/产物三验＋生成指纹/
必判 13 维＋七问/输入隔离/自查交叉/闸判定）＋独立性内容信号：冷读引文实证
（命中草稿原文引文 ≥3 条——未读草稿的空报告 FAIL）/主语污染（报告含
「我写/作为队长」类主上下文人称模式＝非独立 FAIL）/同源判定（审查与自查
维度判定向量全同＝同源伪装 FAIL）/PASS 印章（sha256 重算比对，篡改或
手写伪造＝FAIL 须重跑）。
**无 python 环境＝无法过闸＝不得交付**（交付闸字段唯一合法值「通过」，
不存在无 python 的降验形态）。
**bootstrap 三步（避免先有鸡还是先有蛋）**：账本 `机检运行`／`交付闸` 两字段是 [10] 的输入，
却又须由本次 PASS 来证明——故分两步：
① `python scripts/gatecheck.py <项目目录> --chapter N --precheck`（预检跳过 [10] 两字段）；
② 预检无其他 FAIL 后，把两字段回填 `是`／`通过`（此时有据可依，不是虚标）；
③ 正式跑 `python scripts/gatecheck.py <项目目录> --chapter N` 取 PASS 并交付。
❌ 禁止跳过 ① 直接回填字段；预检报错则先修复再重跑。Windows GBK 控制台可加
`--report <路径>` 把 UTF-8 报告落盘（脚本 stdout 已强制 UTF-8）。机器可验格式：自查覆盖/稽查全覆盖 `X/X`、
审查报告逐行「维度N｜判定｜结论」、各产物末行 `生成指纹: <角色凭证>`、
自查报告落盘为文件（三模式必填，末行 `自查覆盖: X/X 全查`）
（格式规范见 `templates/chapter.md` 铁则⑤与 `core/cold-review.md` 三节）。

## 二、阶段总览

- 确定主角截肢类型与基本处境
- 注入：`core/audience.md`、`genre/{题材}.md`

## 四、人物设定
- **按逐题提问协议收集角色设定**（`core/character-setup.md` 收集流程：

- 产出：`templates/character-card.md`

## 五、大纲
- 搭故事骨架：**四卷体验位**（内容层见 `core/structure.md#五、四卷体验位`；形态层见
  `core/structure.md#四、Volume 层`；实例表填 `templates/outline.md#★四卷规格表`）、章节划分、关键场景
- 弧线与结构规划（`core/structure.md`：四层级/四法则/弧线五组件）
- **开篇切入方式选择**（`core/opening.md`：从维度库选一个维度并标注，禁止默认走 routine）
- 标注哪些场景涉及拐杖/假肢/日常动作/身体细节/亲密/W视角
- **大纲质量闸（进章节写作前须过）**：
  - [ ] 世界观已建立并锁定（无障碍水平/社会态度/器具可得性/**缺失解释框架**，见 `core/worldbuilding.md`）
  - [ ] central question 已定义，且**非默认"她能否接受自己"**（除非题材确为身份认同，见 `core/structure.md`）
  - [ ] **开篇维度已选并标注**（从 `core/opening.md` 维度库主动选择，填入
    `templates/outline.md` 开篇节；「已用开篇维度」已核对避开——见 opening.md 多样性硬约束）
  - [ ] 弧线编排表已填：每段弧线有 question / midpoint shift / crisis / resolution
  - [ ] 每段弧线改变故事**永久状态**，无 filler arc
  - [ ] 招牌元素**剧情契机已标注**（识别各章天然素材契机，不排班分配——
    见 `core/audience.md` 两档供给与 `templates/outline.md` 剧情契机标注）；
    限频预检通过（常规型同一元素两次出现之间至少隔 1 章＝最早 N+2 章再现；8 章健康度预检＝数契机标注表「对应元素」列
    在任意连续 8 章内的去重类数 ≥4，不足提示检查契机标注遗漏）。
    **预检不过时：在契机标注表备注「该章不取用」即可（契机是必要条件非充分条件），
    不回改剧情**
  - [ ] 时间线已排（跨度/间隔/季节无矛盾）
  - [ ] 每章八要素可填（beat / turn / 新信息 / stakes 变化 / 钩子 / 受限 beat + **本章阅读承诺** + **主冲突线 beat**，见 `core/chapter-planning.md`）

  - [ ] **主题材契约已填**（冲突强度档 / 主冲突线 / 基调与基调核心循环 / 创作授权声明，见 `templates/outline.md#★主题材契约`）；

  - [ ] **文风契约已填**：默认叙事距离档 / 声口指纹三条 / 感官主通道 / 禁用腔调
    ＋全书 1–3 个意象母题（首次出现章与变奏计划），见 `templates/outline.md#★主题材契约`；
    **须与账本 `题材契约.文风契约` 同步**（互为正副本，未同步＝冷读按旧契约判漂移）
  - [ ] **篇幅档与计划章数已定**（收集第 12 题 → `计划章数`；**受限配额按此档取值**：

## 六、章节写作
- **逐章硬性要求：禁止一次生成整篇**——不批量产出多章，不一次性写完整本
- 每章循环按所选模式执行（见 `core/workflow.md#〇、工作流模式`：
  flash 自写自审 / pro 写后冷读 / max 队长派单——写作员成文时同样受本节全部约束）
- 逐章写，按场景按需注入专项（拐杖/假肢/日常/身体/亲密/W）
- **写亲密戏前**：读 `topics/intimacy.md` 定档位与边界；B 情色档 / C 成人档再读 `topics/intimacy-explicit.md`
  （B 情色档读 §〇–§七＋§十–§十七，跳过 §八/§九）；先确认账本 `亲密尺度档` 与人物卡 `残端接触边界`，
  **未声明 C 不得写 C**（越档＝本场不成立）
- **开写前核对本章是否在受限配额内**（配额制，按 `篇幅档` 查表；本章可无受限，
  但破窗须补）；
  素材来源：`topics/limitation-scenes.md` 总库 或 `types/{type}.md#受限清单`；
  本章有受限时填入章节模板（templates/chapter.md）三要素：**类型 / 场景 / 她的处置**
  （口径见 `core/chapter-planning.md#二`；同域深挖合法，事件须新或视角新；
  max 模式由队长写入章任务包、写作员执行）
- **开写前过「场景驱动器四问」**（`core/scene-drive.md#七、动笔前的四问`）：
  ① 这一章她动手几次、败在哪　② 对手今天本来想干什么　③ 篇幅第一名是谁　④ 她哪三处不在状态。
  **四问答不出＝这章还没有戏，回去改事件，❌ 不改句子**。这是全书唯一一处
  「停笔回头」比「写完再改」便宜十倍的时机——实测一章改 5 版，返工全发生在句子层，
  而根因每次都在事件层（没有一次"可能失败"的动手）。
- 场景构建（`core/scene-engine.md`：五件事／材料三问／入场晚退场早／细节必须工作）
- **开写前填本章场景—续篇链**，权威 `core/prose-craft.md#一、章节剧情安排`：
  目标／冲突逐拍升级／灾难四型／决定→下一场目标，落进 `templates/chapter-contract.md`
  与账本 `本章登记.场景续篇链`；逐场连接词只许「因此／但是」，❌「然后」＝断链，
  回炉重排 beat。链检与「立场→后果」四环属**规划动作**，❌ 不是事后润色项
- 每个涉及截肢细节的场景，先读对应专项再写
- **用户指令优先（先于本关卡）**：本章变更若来自**用户显式指令**，走
  `SKILL.md#★用户指令优先`——直接改大纲、给章号、告知影响、登记 `用户指令变更`，
  **不再走「向用户说明并确认」**；本关卡只约束 AI 自主新增（无用户原话＝自主新增）。
  用户命令要求提前的节点，**不受下方「大纲节点消费自查」限制**——提前消费禁令
  只约束 AI 自主提前，不约束用户命令。
- **大纲变更确认关卡（例外③，每章开写前过；仅约束 AI 自主新增）**：本章拟引入的悬念线/暗线/设定/
  重要角色动机（hook-bearing——构成后续章期待/悬念源/伏笔的元素；本章内消化的
  装饰性细节不溯源，防误伤正常人物塑造）**逐项溯源大纲**——
  大纲内存在的元素直接写；大纲不存在且**非用户指令**的元素属大纲变更，
  须向用户说明并确认后方可写入（AI 不得自作主张扩充大纲）；未经确认的私加＝严重错误
  第 4 类（`SKILL.md#三`，整章回炉）。确认通过的新元素登记进账本 `大纲对齐`
- **大纲节点消费自查**（仅约束 AI 自主提前）：大纲后置章的爆点素材（危机爆发/最大受限/关键转折/卷末大钩）
  本章只能铺垫不得以 ≥半强度提前写出（提前消费＝严重错误第 4 类）；
  **用户显式指令要求提前的，按用户指令执行并登记 `用户指令变更`**。
- 产出：`templates/chapter.md`（max 模式另产出章任务包与章草稿文件）

## 七、润色

## 十、架构层接口（四方向落地＋宿主接入层＋hook 平台转变＋小上下文适配）

> 本节只给**接口与执行顺序**，规则本体在 `rules/rules.yaml`、解释与示例仍在各专项文件。
> 平台能力差异与降级声明见 `PLATFORM-CN.md`；**任何一层降级必须写进账本 `工作流执行日志`**，

### 10.1 开写前（每章）

1. **合规前置验证**（国内平台第 0 步，见 `PLATFORM-CN.md`）——未通过不得开写。
2. **注入硬层**：整段读 `rules/hard-layer.md`，❌ 不摘要、不参与语义检索。
3. **编译检查**：`python scripts/compile_rules.py` → 非 PASS 先改齐口径（可离线跑、可挂 CI）；
   维护期改库后的完整自检另跑 `python scripts/verify.py`（编译检查＋库内自检一次跑完）。
4. **展开本章规则包**：`python scripts/query_rules.py --genre <题材> --type <类型> --tier <尺度档> --mode <模式> --chapter-kind <章型> --conflict <冲突强度档> --chapter <N> --no-hard-layer`
   → 产出规则包文本：**按 `scope` 展开，当前以题材大类为主**；类型 / 尺度档 / 模式 / 冲突强度档 / 章型 / 章号
   仅作坐标标注，不参与过滤（`scope_key` 是预留维度，见 `rules/rules.yaml` 头部 scope 约定）。
   → 据此填写 `templates/chapter-contract.md`。参数取自账本，结果确定，不靠 AI 判断读哪些文件。
   ⚠ `--out` 须指向**项目目录**，❌ 不得覆盖技能目录内的模板骨架。
   ⚠ `--no-hard-layer` 前提＝第 2 步硬层已整段注入；未注入（无 shell、宿主只拼这一份规则包）时
     去掉该参数让规则包自带硬层全文。两种形态不可叠加、也不可都省（默认形态见 host-hooks.yaml）。
   **小上下文机型可加 `--format compact`**（规则断言截 60 字/条；与 `--no-hard-layer`
   叠加后规则包约 3.7 KB）——代价：规则细节不在场，
   **凡涉动作/生理/辅具的写法须回读源文件**（compact 档只作索引）。
5. **章契约落盘**：填好的章契约存为**项目目录** `chapter-contract-N.md`（与规则包同级，❌ 不留在
   上下文里）——防上下文压缩丢失写作计划；每章开写前从盘上重读。
   ⚠ **v9.4 卡口**：写作卡末尾「四行硬项」（动手与失败点／对手今天想干什么／篇幅第一名／
   三处不在状态）**必须逐行答完才能开写**，`gatecheck [27]` 会机检非空。
   四行空着或填「无」＝这章还没有戏，**回大纲加事件**——这是全流程最便宜的一次返工点。
   （实测：一章写 5 版仍在返工，根因不在句子，在「这一章没有任何一次可能失败的动手」。）
6. **状态推进**：`python scripts/state_machine.py --ledger <账本> --advance 已规划`
   → 合法转移由代码判定；跳步直接报错。
   落盘为**文本级推进**（只改写账本「章节状态」块内 当前态/轨迹 两行，
   注释与手写格式逐字保留）；轨迹为跨章累计（「已交付 → 待规划」回卷即设计）。
7. **写作时点不回读 SKILL.md**：规划完成进入写作后，规则包＋章契约＋硬层就是
   **唯一在场视图**（合计约 14 KB，实测）；SKILL.md 的注入索引是收集/规划阶段的工具，写作阶段
   不必常驻——❌ 禁止以「再确认一下总纲」为由回读 28 KB 全文，缺什么读规则包指向的源文件。

### 10.2 写作与交付（顺序不可跳）

> **本节是三模式章循环的权威交付顺序**（上文 flash/pro/max 概览以本节为准）：flash 跳过冷读/红队/复核轮（自写自审），

未落盘尾部」，重写代价从整章降到一段；已交付章的 gate-pass SHA 不受影响
（追加完成后再跑机检）。

❌ 不分 beat 多轮生成（每轮重复注入规则包是纯 token 消耗；「写了后段忘前段」
靠章契约在场解决，不靠多轮）。pro/max 不变（分段是审查需要，不是写作需要）。

`章节状态.轨迹`）→
`python scripts/validate_output.py --project <项目> --chapter N --repair-hint` →

### 10.3 压缩恢复协议（小上下文机型必读）

> 本技能体量大（SKILL 28 KB＋规则包＋账本），小上下文模型**第一章成文前很可能压缩一次
> 甚至多次**。压缩丢的从来不是「状态」（账本/草稿/报告都已落盘），而是「注入」——
> 硬层、本章规则包、章契约、人物设定细节都活在上下文里，摘要最爱丢禁令细节。
> **协议**（每次接到写作/续写指令时执行）：

1. **触发自检**：确认三件套在场（硬层＋本章规则包＋章契约）。判据极简——
   「我能引用 hard-layer 的禁令原文吗」；不能＝疑似被压缩，走恢复。
2. **最小恢复集**（合计约 14 KB，按序重读，❌ 不重建全量）：

   | 序 | 文件 | 体积 | 作用 |
   |---|---|---|---|
   | ① | `rules/hard-layer.md` | 4.3 KB | 禁令基线（最优先——丢了它，写出的错误机检查不出） |
   | ② | 项目目录 `chapter-rules-N.md` | ~8.6 KB | 本章规则包（query_rules --out 落盘产物） |
   | ③ | 项目目录 `chapter-contract-N.md` | ~3 KB | 本章写作计划（防偏题） |
   | ④ | 账本「章节状态」＋「角色固定属性」块（**含「声口」与「人物活性锚」**） | ~1 KB | 坐标、进度与「这个人是谁」 |
   | ⑤ | 上一章末尾 ~500 字 | ~1 KB | 风格与钩子衔接 |

   > ⚠ **第 ④ 件不可只回读坐标**：人物活性锚（声口 / 核心欲望 / 软肋 / 处置风格）
   > 必须与坐标块一起重读。压缩后的「合规但呆板」几乎都出在这里——禁令全在、
   > 人物没了；正面规则见 `core/style.md#★人物活性`，字段定义见 `templates/character-card.md`。
   > ⚠ 恢复的是**立场与声口**，不是一套精巧动作模板（见 `core/style.md#★伪活性判定`）。
   > ⚠ 第 ④ 件另须回读账本 `题材契约.文风契约`（默认距离档／声口指纹／
   > 感官主通道）与 `distribution.文风指纹` 近 5 章、`distribution.意象母题`——
   > 压缩后「单章合规、全书换腔」几乎都出在这里；恢复的是**文风坐标**，❌ 不是重设一套新风格。

3. **恢复后核对**：对照账本「工作流执行日志」的注入登记，缺口补齐再开写。
4. **恢复留痕**：恢复动作记一行日志（「第 N 章：压缩恢复协议触发，重读①②③」）——
   压缩发生是**可审计事件**，不是静默的；连续两章触发＝提示用户考虑 compact 规则包档。
5. **宿主 hook 平台**：Claude Code 等有 PreCompact 事件的平台由 hook 自动执行
   （见 `host-hooks.yaml` pre_compact）；无 hook 平台按本节人工协议执行——
   规则常驻型平台已含同款条款。

> ⚠ 冷读独立性：无真子代理的平台**不得**用同会话角色扮演顶替后仍称「独立冷读」；
> 须在日志写明「独立性声明作废，质量等级降为自审」（见 `PLATFORM-CN.md`）。
> 状态机映射：红队验证归入「已冷读」态，**不单独设态**；8 态定义见 `rules/rules.yaml chapter_states`。

### 10.4 离线（不进创作上下文）

  **编译检查是全平台最硬的保证**（不依赖 agent 愿不愿意执行），离线优化器只是辅助评估工具。

### 10.5 边界（务必读）

机检、编译检查、Schema、状态机只保证**可形式化**的项。

### 10.7 其他平台安装后注册（hook 兼容层）

`.claude/` 会被国内平台安装器忽略——hook 语义的单一事实源是 `host-hooks.yaml`，
安装到其他平台后转变注册（详见 `SKILL.md#一、安装后注册`）：

- `python scripts/install-host-hooks.py --platform <平台> --project-dir <小说项目目录> --yes`
- 事件钩子型→等价注册（宿主强制）；规则常驻型→平台规则目录生成规则文件
  （强制力降级显式声明）；未核实平台→不猜测写入（exit 3＋人工注册指引）
- 无 shell 平台按 `host-hooks.yaml` 人工注册，降级声明写进账本「工作流执行日志」。

## 十一、注入原则
- 不主动全量加载专项，写到哪读到哪
- **成文工艺按需分层**：`core/prose-craft.md` 第一节在**章级规划**读、
  第三/四/五节在**润色**读；❌ 不随 `rules/hard-layer.md` 整段注入、不进全量加载
  （写作时点在场视图仍＝硬层＋规则包＋章契约＋账本坐标，约 14 KB；
  R-024 的摘要随规则包展开，细节回读源文件）
- 类型差异小节用 `types/{type}.md#X` 叠加
- **「不注入」优先于「注入」**：分支（上肢截肢分支／无辅具分支）的 `不注入` 清单，
  优先级高于任何同名的场景触发项——先过不注入清单，再决定读什么
- **更具体的分支优先**：同一专项被多处引用时，按"具体 > 通用"取
  （无辅具分支 > 一切移动相关；上下肢复合 > 上肢截肢分支／下肢默认分支）
- **同一专项的"规划侧"与"写作侧"不是一回事**：`章级规划…beat`（开写前取类与配额）
  与 `写到…场景`（写作时取用法）指向同一文件时，按各自阶段各读一次，不得合并成一次
