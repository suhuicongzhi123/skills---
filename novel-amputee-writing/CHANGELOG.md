## [5.14.0] - 2026-10-27 · 用户指令优先（剧情变更的最高权限）

- **动因**：原库只有「AI 不得私加」与「大纲变更须确认」，没有「用户命令改大纲」的正规路径——
  用户指定剧情时，AI 要么以「基调锁定/大纲已定」拒绝，要么改动后被判「大纲外私加」第 4 类。
  本次把「锁 AI」与「锁用户」分开：**契约约束 AI 的自主改动，不约束用户**。
- **新增 `SKILL.md#★用户指令优先`**：
  - 权限顺序：**用户指令 > 大纲契约 > AI 自主判断**
  - 三类变更：**A 用户显式指令**（直接改，不请求确认）／**B 用户模糊偏好**（转密度/位置）／
    **C AI 自主新增**（仍走确认；未确认＝私加）
  - 五步：复述指令 → 可行性判断 → 改大纲 → 给章号 → 登记
  - 固定四行告知：收到 / 呈现 / 大纲改动 / 代价
  - 「尽快」量化：P0＝N+1、P1＝N+2、P2＝N+3；超 3 章须用户同意；用户给章号以用户为准
  - 冲突处理：与已写章冲突给三选项；基调/主线让路；三条硬闸不关闭；改口以最新指令为准
  - 防滥用：必须有用户原话；不得夹带；无登记＝私加
- **`core/chapter-planning.md` 新增「七、用户指定剧情的插入与提前」**：
  五种插入法（插入/替换/压缩/前置/重写）、四问判据、插入后六项检查、告知与登记、尽快接口
- **挂接**：`SKILL.md` 强制约束加例外④＋第 4 类加用户指令例外＋注入索引加触发；
  `core/workflow.md` 大纲质量闸/章节写作关卡分流/账本状态更新；`core/cold-review.md`
  输入清单＋维度 19/20 豁免；`templates/outline.md` 契约改「AI 锁定；用户可变更」＋
  `用户指令变更记录` 表；`templates/state-ledger.yaml` 加 `用户指令变更` 块；

## [5.12.2] - 2026-10-27 · 更新检查「最新 tag」解析修复（字典序陷阱）

- **验证发现（更新链接指向核查）**：仓库/安装/拉取 URL 全部正确且与远端一致；
  但 SKILL 〇 节两条检查方法的「取最新 tag」解析各有陷阱——
  ① `git ls-remote --tags` 输出按 ref **字典序**排列：取末条会得到 v5.9.0 而
  实际最新 v5.12.1（`v5.9` 字典序大于 `v5.12`；同理 v5.13.0 永远排在 v5.4.0
  之后取不到）——实测实证
  ② GitHub API `tags?per_page=1` 按**创建序**返回：回退期补打的 tag 晚于更高
  版本创建，当时调用会返回补打 tag 而非版本最新
- **修复**：方法 1 明确「版本语义排序取最大（sort -V | tail -1），禁止取输出
  末条」并附实测陷阱说明；方法 2 明确「返回值只可与本地 version 比大小，
  不得默认其为版本最新」＋tag 号解析须 x.y.z 三段数值比较，禁用字符串比较
- 附：归档口径执行（v5.9.0 压入归档区，维持近 6 版全文）

## [5.12.1] - 2026-10-27 · 哈希基线行尾归一（自检误报修复）

- **现象**：selfcheck [5] 报「gatecheck.py 哈希基线不符」——基线按 CRLF 磁盘
  版本计算，在 LF 行尾环境（fresh clone / autocrlf 差异）下必现误报
- **根因**：[5] 按原始字节（二进制读）哈希——行尾敏感；git autocrlf 使磁盘
  行尾随克隆环境漂移（repo 存 LF，Windows 检出 CRLF），基线取自哪种行尾，
  另一环境即误报「被篡改」
- **修复**：哈希前归一行尾（
→
），基线按归一值重算（533031bb）——
  LF/CRLF 双形态实测 PASS；gatecheck 内部哈希（印章/正文SHA）经文本模式
  读取（universal newlines 自动归一）本就免疫，无需改动
- 附：归档口径执行——新增 5.12.1 后 v5.8.0 压入归档区（维持近 6 版全文）

## [5.12.0] - 2026-10-27 · 注入性提示词体系（执行者身份——三层 persona）

- **动因**：实测失效史（脚本漏跑/分角色扮演/深刻感漂移/自查全绿）共同根源是
  动机层缺失——规则是外部拉力，会被长上下文稀释；persona 以「我是谁」参与
  每次生成决策，是卡口体系未用过的正交维度（冷读子代理调用 prompt 早已用
  persona framing 且实测有效——子代理有身份，主流程却从未有过）
- **三层注入结构**（不新建文件，随库分层）：
  - **主 persona**（SKILL.md 总纲·库定位声明后，激活即常驻）：「截肢题材写作
    工坊的主笔兼质量总监」身份＋四条行为契约（为特定读者写作＝约稿合同/
    生理事实是看家本领/纪律是职业底线——订单·走货路线·主菜·不复述/
    交付诚信是手艺凭证——登记即事实·自问是肌肉记忆）
  - **分角色上岗声明**（workflow 〇 节 max 细则）：队长（工坊主理人——订单在
    手、走货不换道、手续齐全）/写作员（领活的写手——生理事实零错是本分、
    受限戏是主菜、不越权）/记账员（唯一写账的账房——账实相符）；审查员
    上岗声明入 cold-review 五节（目标读者＋考据编辑双视角，接现有「独立
    稽查子代理」头）
  - **质检视角句**（chapter.md 核查清单顶）：「自查时你不是作者，是刚接手的
    质检编辑」——治自查全绿的心理学杠杆
- **设计要点**：限定「执行本技能期间生效」不做全局身份声明（不与宿主
  system prompt 冲突）；persona 与规则同源同限（拦不住蓄意造假）——定位为
  卡口的动机层补全而非替代
- 联动：SKILL 版本 5.12.0

## [5.11.1] - 2026-10-27 · 恢复 v5.11.0 基线＋并入脚本漏跑针对性封堵

- **版本路线修正**：经重新评估，恢复 v5.11.0 全部内容（从 tag v5.11.0 检出，
  历史保留 v5.6.1/v5.6.2 提交与全部 tag）；v5.6.2 的脚本漏跑针对性调整
  （在 v5.6.0 基线上落地）并入本版
- **并入的脚本漏跑封堵（源自 v5.6.2，适配 v5.11.0 基线）**：
  - **脚本运行＝交付显性前置条件**：gatecheck 实际运行＋输出 PASS 是
    「交付闸: 通过」的唯一合法来源；三模式章循环加显性步骤
    「运行 gatecheck（自问：脚本跑了吗？）→ PASS → 携机检披露交付」
  - **脚本漏跑＝严重制度失败**：SKILL 〇-补 第 6 类扩为「脚本漏跑与篡改
    验证机制」两类制度级失效——漏跑即整个验证体系未生效，交付整体无效
    （无论正文质量）；发现漏跑须在对话中如实披露＋补跑＋重新交付，
    隐瞒＝制度失败＋诚信违规双重叠加
  - **自问铁律＋披露义务**：「脚本跑了吗」落三处（章循环引语/章末核查
    清单⑥脚本自问/账本 `机检运行` 字段）；交付必附披露行
    「机检：PASS（第N章…）」
  - **机检新校验**：gatecheck [10] 扩——`机检运行` 字段须为「是」
    （非「是」＝漏跑态 FAIL）；selfcheck 哈希基线随 gatecheck 变更重算
- **如实声明（边界不变）**：本组机制是提示层显性化——把「跑脚本」从隐含
  步骤变为不可忽视的显性动作与披露义务；绝对强制（AI 无视一切提示仍漏跑）
  仍需宿主级 hook，超出技能包能力
