## [5.12.0] - 2026-10-27 · 注入性提示词体系（执行者身份——三层 persona）

- **动因**：实测失效史（脚本漏跑/分角色扮演/深刻感漂移/自查全绿）共同根源是
  动机层缺失——规则是外部拉力，会被长上下文稀释；persona 以「我是谁」参与
  每次生成决策，是卡口体系未用过的正交维度（冷读子代理调用 prompt 早已用
  persona framing 且实测有效——子代理有身份，主流程却从未有过）
- **三层注入结构**（不新建文件，随库分层）：
  - **主 persona**（SKILL.md 总纲·库定位声明后，激活即常驻）：「截肢题材写作
    工坊的主笔兼质量总监」身份＋四条行为契约（为特定读者写作＝约稿合同/
    生理事实是看家本领/纪律是职业底线——订单·走货路线·主菜·不复述/
    交付诚信是手艺凭证——登记即事实·自问是肌肉记忆）
  - **分角色上岗声明**（workflow 〇 节 max 细则）：队长（工坊主理人——订单在
    手、走货不换道、手续齐全）/写作员（领活的写手——生理事实零错是本分、
    受限戏是主菜、不越权）/记账员（唯一写账的账房——账实相符）；审查员
    上岗声明入 cold-review 五节（目标读者＋考据编辑双视角，接现有「独立
    稽查子代理」头）
  - **质检视角句**（chapter.md 核查清单顶）：「自查时你不是作者，是刚接手的
    质检编辑」——治自查全绿的心理学杠杆
- **设计要点**：限定「执行本技能期间生效」不做全局身份声明（不与宿主
  system prompt 冲突）；persona 与规则同源同限（拦不住蓄意造假）——定位为
  卡口的动机层补全而非替代
- 联动：SKILL 版本 5.12.0

## [5.11.1] - 2026-10-27 · 恢复 v5.11.0 基线＋并入脚本漏跑针对性封堵

- **版本路线修正**：经重新评估，恢复 v5.11.0 全部内容（从 tag v5.11.0 检出，
  历史保留 v5.6.1/v5.6.2 提交与全部 tag）；v5.6.2 的脚本漏跑针对性调整
  （在 v5.6.0 基线上落地）并入本版
- **并入的脚本漏跑封堵（源自 v5.6.2，适配 v5.11.0 基线）**：
  - **脚本运行＝交付显性前置条件**：gatecheck 实际运行＋输出 PASS 是
    「交付闸: 通过」的唯一合法来源；三模式章循环加显性步骤
    「运行 gatecheck（自问：脚本跑了吗？）→ PASS → 携机检披露交付」
  - **脚本漏跑＝严重制度失败**：SKILL 〇-补 第 6 类扩为「脚本漏跑与篡改
    验证机制」两类制度级失效——漏跑即整个验证体系未生效，交付整体无效
    （无论正文质量）；发现漏跑须在对话中如实披露＋补跑＋重新交付，
    隐瞒＝制度失败＋诚信违规双重叠加
  - **自问铁律＋披露义务**：「脚本跑了吗」落三处（章循环引语/章末核查
    清单⑥脚本自问/账本 `机检运行` 字段）；交付必附披露行
    「机检：PASS（第N章…）」
  - **机检新校验**：gatecheck [10] 扩——`机检运行` 字段须为「是」
    （非「是」＝漏跑态 FAIL）；selfcheck 哈希基线随 gatecheck 变更重算
- **如实声明（边界不变）**：本组机制是提示层显性化——把「跑脚本」从隐含
  步骤变为不可忽视的显性动作与披露义务；绝对强制（AI 无视一切提示仍漏跑）
  仍需宿主级 hook，超出技能包能力

## [5.10.0] - 2026-10-26 · 交付正文深度绑定（外部卡口审查报告采纳）

- **动因**：外部审查报告（v5.9.0 三轮红队实测）确认——被机检的是磁盘章草稿，
  交付给用户的可以是另一份文本（flash 下草稿甚至不必存在）：交付与被检脱钩
  是零成本路径 D。本次以「正文与脚本深度绑定」为核心封堵
- **绑定三件套**（gatecheck [14] 重构＋workflow 卡口③/交付正文绑定节）：
  ① 章草稿升为**三模式必需产物**（flash 也必须落盘——无文件＝无交付物＝FAIL）
  ② 印章哈希链纳入章草稿：印章＝sha256(章号+**章草稿**+自查+审查)[:16]——
  交付正文被替换 → 印章失效 ③ gate-pass 升为**交付凭证**：内含
  正文SHA（sha256(章草稿)[:16]）＋正文字数＋印章；重验时双比对（SHA 与
  印章各算各的）——正文被换 → SHA 不符 FAIL；交付时随正文附凭证内 SHA
  与字数（贴出即可，不要求用户判断——正文与被检文件不一致立即可见）
- **FAIL 运行不生成交付凭证**（原缺陷：FAIL 的那次运行也会补写印章）——
  凭证只在整体 PASS 时生成；修复后重跑
- **顺修三处口径**：P1-6 工作流执行日志注释明确「不参与滚动窗口归档」
  （归档断链＝机检 FAIL 的规则矛盾）；P1-7 chapter.md「冷读子代理稽查
  （可选）」残留改「pro/max＝必做；flash＝不适用」；flash 产物行同步章草稿
- **报告其余项待裁定**（本次未做）：默认 flash→pro（P0-1）、自查清单稳定 ID
  全集校验（P0-2）、机检输出对用户可见化（P0-3）、同源阈值比例制、判定值
  枚举、记账员产物绑定、短篇口径声明、大纲列 ch1 前置产物、selfcheck 校验
  gatecheck 哈希基线
- 联动：SKILL 5.10.0＋交付闸条目；state-ledger 草稿注释（三模式必需＋
  绑定基准）＋日志注释（不归档）

## [5.8.0] - 2026-10-26 · 卡口去人工化（无人工介入版——独立性内容信号＋PASS 印章）

- **动因**：用户铁则——卡口不得依赖人工介入（「依赖用户人工审查是绝对失败；
  人工审查一眼便知，还要限制卡口做什么」）。v5.7.0 的交付验证包（用户持凭证
  向宿主查证）、人工冷读（用户扮演冷读者）、凭证「查证权在用户」三个机制
  全部违反铁则，废除；要求：用户不介入下 AI（尤其单 agent 环境）偷懒绝不能
  交付，必须重跑完整流程
- **废除人工依赖机制 3 处**：交付验证包（改为 PASS 印章机检）；人工冷读节
  整节删除（无能力环境唯一出路＝flash，pro/max 无子代理替代形态——能力闸
  无豁免收紧）；交付闸「人工验」态删除（唯一合法值「通过」；无 python 环境
  ＝无法过闸＝不得交付）
- **新增独立性内容信号（无人工可机检，gatecheck [12]-[14]）**：
  - **[12] 冷读引文实证**：审查报告中命中本章草稿的原文引文（「」内 ≥8 字）
    ≥3 条——零命中＝未真实读草稿的空报告 FAIL（抄规则术语不计数，逼真读）
  - **[13] 主语污染**：审查报告出现「我写/我设计/作为队长/我刚才」类主上下文
    人称模式 → FAIL——独立子代理没有创作过程记忆，出现即判非独立
    （单上下文分角色扮演的机检级判据）
  - **[14] 同源判定**：审查报告与自查报告 22 维判定向量完全一致 → FAIL
    ——独立视角必有权重差异，全同＝同源伪装强信号
- **PASS 印章（gatecheck [15]）**：脚本 PASS 时自动生成 `gate-pass-第N章.txt`
  （末行印章＝sha256(章号+自查报告+审查报告)[:16]，脚本生成手写无效）；
  运行时对已存在印章重算比对——产物事后篡改/手写伪造 → FAIL → 须重跑完整
  流程重新过闸；规则固化「下章开写前重验上章印章」——历史伪造在任何后续
  真跑中被揭穿
- **架构边界声明（写入脚本头与 workflow，不可回避）**：gatecheck 由 AI 自行
  执行——提示词技能无法强制 AI 运行验证（执行权在被监督者手里）。强制力
  模型＝**验证网＋成本压制**：过闸嵌入每章循环＋机检内容信号把「伪造合规
  全套」成本抬到高于真实执行（偷懒须真读草稿凑引文+编差异化判定+正确算
  印章哈希——此时伪造已不是偷懒）；绝对强制需宿主级 hook，超出技能包能力
- 联动：cold-review 受理前验收四判据→六判据（+引文实证/主语纯净）；
  五-补人工冷读节删除、失察追责节号回收（五-补2→五-补，全库引用同步）；
  state-ledger 删冷读形态/人工验态；character-setup 末题删人工冷读选项；
  SKILL 版本 5.8.0
