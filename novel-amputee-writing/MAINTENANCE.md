> 本文件是给改这个技能的人看的。它**不进创作上下文**，不参与注入索引，
> 也不含任何写作规则。创作期读到这里的任何一条，说明读错了文件。

> **目录（>100 行按需文件，勿整体加载）**：一 正式技能规范符合性｜二 文件职责分工｜三 编号体系｜四 改动流程｜五 改法铁则｜六 历史坑。

## 一、正式技能规范符合性

| 项 | 要求 |
|---|---|
| 元数据 | frontmatter 只留 `name`（小写连字符、与目录名一致）、`description`（第三人称、含何时使用/不触发、无尖括号）、`version`、`author` |
| 三层披露 | ① name＋description 常驻；② `SKILL.md` 只放行为契约、最高优先级规则、工作流骨架、注入索引、严重错误分级；③ 详细规则进 `core/` `types/` `topics/` `genre/` `templates/` `rules/` `eval/`，保持一级深引用 |
| 单一权威 | 同一规则只在一处立定义；索引注释是导航摘要，不是规则权威 |
| 写法 | 规则正文用祈使/不定式。例外：`SKILL.md#★执行者身份` 的第二人称是行为契约 |
| 自包含 | 包内资源自足；仓库根 `.claude/` 属可选增强层，缺失时按 `PLATFORM-CN.md` 声明降级 |
| 校验 | 改完跑 `python scripts/verify.py`；改 `scripts/gatecheck.py` 后须先 `python scripts/selfcheck.py --update-baseline` 重算基线 |

## 三、编号体系

- `S01–S50`：章末自查项编号，**保留不重排**。其中 12 组为必过集（写作报告只列这 12 组），
  其余降为后台条款，供维护排查时查阅。
- 冷读维度 `1–22`：保留不重排。13 维为必判集，其余在本章相关时判；读感问 1–7 共七问。
- `R-001–R-034`：规则 IR 编号，与 `rules/rules.yaml` 一一对应。
- 机检编号 `[1]–[31]`（`[30]` 幻想向真打／`[31]` 默认性格与题材分割）；
  章末自查 `G01–G12` 12 组、冷读 22 维、必判 13 维三组计数**不因新增规则变动**——
  新规一律挂既有组与既有维度，❌ 不新增编号。
- 新增规则一律追加编号，不复用废弃编号。
- **小节标题编号**：`##` 用中文数字（〇 一 二 …）按出现顺序连续编号；`###` 用阿拉伯 `x.y`
  （x＝所属 `##` 的序数，y 顺延）。❌ 不用 `x.补`／`-bis`／`-ter`／字母后缀（如 `16.1-b`）等插入号——
  新增小节顺延主序，不留补号；标题不带版本号／「原§X」／「编号说明」等注释。
  素材 catalog（`F`／`M` 等）同样连续编号（如 `F0b` 已归并为 `F40`），❌ 字母后缀。
  **>100 行的按需文件顶部置目录**（`> **目录（>100 行按需文件，勿整体加载）**：…`），改标题须同步目录与全库引用。

## 四、改动流程

0. **先打包备份**：`tar -czf _backup/<技能名>-<版本>-<时间>.tar.gz <技能目录>`。
   改脚本尤其必须先备份——见第六节第一条。
1. 改口径 → 先改 `rules/rules.yaml` → 跑 `compile_rules.py`
2. 改规则正文 → 同步 `rules/hard-layer.md`（若属常驻层）
3. 改 `scripts/gatecheck.py` → `selfcheck.py --update-baseline` → `verify.py`
4. 改编号或计数 → 同步 `templates/chapter.md`、`core/cold-review.md`、`eval/eval-set.yaml`
5. 改枚举 → **两处同改**：`templates/state-ledger.yaml` 末尾 `枚举表` 数据块 ＋
   `gatecheck.py` 常量（`[25]` 会在不一致时提示）
6. 全部 PASS 后按第五节语义递增版本号（四处同改＋`README.md` 同步），
   倒序记 `dev/CHANGELOG.md` 并标注性质

## 五、改法铁则（总纲；改动流程须遵守）

> **标准改法**：口径错了就改**权威源那一行原文**——错误的表述就地改成正确的，
> 多余的行、段、文件直接删；同一口径的正副本同批改齐；改完人工逐文件通读复核，
> 脚本只作辅助。**纠错类维护**不新增条款、不新增文件、不新增章节
> （新增功能另按下方 SemVer 计 MINOR）。

- **❌ 禁止打补丁**：不允许新增「★XX 只写一次」「反向闸」「按更严口径」「vX.Y.Z 新增」
  一类条款去压住旧错误。旧条款错就改旧条款本身；补丁与根源并存会形成两版口径，
  每打一次补丁库就长一截，问题却还在。发现补丁式条款＝按本铁则回炉重写。
- **❌ 禁止注释式纠错**：不允许在原文旁加 `⚠`／`>`／`（…）` 括注解释「其实应该怎样」。
  直接改正文。括注不会被检索召回，且下一段仍会按未改的旧文本执行。
- **错误文件、多余文件一律删除**：转发桩、重复正副本（只保留权威一处）、
  因口径变更已失效的文件、纯历史残留文件，直接删文件，❌ 不新建「归档／说明」文件
  承载被删内容；删前查全库引用并同步改指针（`verify.py` 悬空检查兜底）。
- **体量硬约束**：纠错类改动**只减不增**——删掉的旧口径不得用新条款、括注或新文件补回；
  新增规则必须有对应的新功能，优先并入既有条目，❌ 不复制既有内容、❌ 不新建同名文件；
  索引只做导航，`dev/CHANGELOG.md` 只记当次变更并按归档口径压历史全文；文件数只减不增。
  连续两版无新功能却净增＝先精简再继续，避免体量无限膨胀。
- **人工二次审查**：不依赖脚本机检结论。逐文件通读改动与交叉引用，
  查「旧口径是否还有残留」「正副本是否同步」「删掉后指针是否悬空」；
  `compile_rules.py` / `selfcheck.py` / `verify.py` 只作辅助。

### 版本号语义递增（SemVer）

| 段 | 触发 | 例 |
|---|---|---|
| **MAJOR** `x.0.0` | 不兼容：目录结构重组、废弃/删除文件、注入索引或工作流模式变更、既有稿子按新库会被判不通过 | 9.x → 10.0.0 |
| **MINOR** `x.y.0` | 向后兼容的规则新增：新增规则条目／机检项／审查落点／题材包／维护纪律 | 9.6.0 → 9.7.0 |
| **PATCH** `x.y.z` | 向后兼容的修正：口径纠错、冗余删除、联动同步、指针／计数／哈希修正 | 9.7.0 → 9.7.1 |

- 一次维护**只升一次**，按上表取最高级别；改动量不参与定级，
  ❌ 不得因「改得多」跳到 MAJOR，❌ 不得复用或回退版本号。
- 四处同改：`SKILL.md version` / `rules/rules.yaml skill_version` /
  `host-hooks.yaml skill_version` / `eval/eval-set.yaml skill_version`；
  仓库根 `README.md` 版本表与版本说明同步；`dev/CHANGELOG.md` 倒序加当次条目并标注性质。
- 维护者手册本身（不进创作上下文）的改动按其内容性质计入当次版本，不单独占号。

## 六、历史坑（不影响写作，只影响改库）

- **改文件用编辑工具，不要用脚本就地 `open(p,'w')`**。一条命令 `io.open(p,'w',encoding=...,newline='...')`
  只要参数非法，异常在 `open` 阶段就抛出，**而文件此时已被截断**——一个 62 KB 的脚本会瞬间变 0 字节。
  实测发生过，靠备份恢复。批量替换请用编辑工具的精确替换，或先写临时文件再整体替换。
- 两处副本漂移是历史第一故障源：口径只留一处，其余指针
- 脚本改动不同步哈希＝交付闸整体失效
- 删文件前先查全库引用，`verify.py` 的悬空检查会兜底，但引用改起来比新建文件贵
- 示范句照抄与公式化改写都会成为新模板指纹，加示范时优先加**判据**而不是加句子
- **判据只写在脚本里等于没写**：冷读读不到脚本注释。任何机检在做的事，规则文件里必须有
  对应的一句话，否则两边会算出两套数字（实测：段落基准一个按全段 49.5%、一个按叙述段 35%，
  双方都「有据」）
- **别用「引文命中率」判报告与正文脱节**：审查报告的引号还用于举反例、给改法、引账本原文，
  那些本来就不在正文里。要判脱节，用可数的事实（如 `复核字数: N` 比对）
- **写反例时必须带「禁止／❌／反例／不写」之一**：`selfcheck [3]` 靠这几个词判断
  「这是禁令句」还是「这是复发」。实测：在 `PLATFORM-CN.md` 写一句反例清单「搜 `蹲不下` 等词」
  （本意是让人去搜），被自检判为「蹲豁免口径复发」。**这不是 bug，是词表机制的必然**——
  它读不出你的意图。以后凡是「把违规词写进规则文档当例子」，同一行必须带上述关键词。
- **新增机检项必须同时补「无 shell 替代」**：`gatecheck` 跑不了的平台占多数，
  只在脚本里实现的检查，对那台机器等于不存在。每加一项，同步写进
  `PLATFORM-CN.md#四、无 shell 平台的手工替代清单（必读）`，否则强制力只覆盖一半机器。
- **版本号只按第五节 SemVer 定级**：9.4.0 一度误标 10.0.0 被要求回退，
  原因是把「改动量大」当成 MAJOR；定级只看兼容性，不看改动量。
- **示例必须抽象化，不得出现任何具体作品的专名**（实测）。这是最隐蔽的一类污染：
  写规则时手边正好有一部正在写的稿子，**它是最顺手的例子来源，所以最容易写进去**。
  实测两轮都中了——第一轮的章节名（两个字的标题）、原文台词、一整段变形描写进了强度层；
  第二轮的三个配角名、主角的招牌动作、两处原文台词进了情绪层与成文层。
  后果不是"泄露剧情"，是**技能变成只对那一部书有效的规则集**，换题材就失效。
  - **做法**：示例只写**类型**（"长期一个人过日子的人""刚入行的年轻人"），
    不写具体人名；引原文只引**自造的中性句**，不引稿子里的句子；
    数据表格用"样本 A／样本 B"，不用章节名。
  - **判据**：把示例单独抽出来，能不能看出它属于哪一部作品？看得出＝不合格。
  - **为什么不能自动化**：专名无法穷举，词表一旦建立，词表本身就是残留。
    这一条只能靠写入时的自觉 + 交付前的抽读。
